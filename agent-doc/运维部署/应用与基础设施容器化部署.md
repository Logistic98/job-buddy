# Docker Compose 应用与基础设施部署

## 目标与边界

本方案用于在具备 Docker Compose 的 Linux 服务器部署 JobBuddy，支持两种正式模式：

- 仅应用模式：只加载 `docker-compose.yml`，启动八个应用服务，PostgreSQL、Redis 和 MinIO 使用环境文件中已独立部署的地址。
- 完整模式：依次加载 `docker-compose.yml` 和 `docker-compose-infra.yml`，在同一个 Compose 项目中启动八个应用服务以及 PostgreSQL、Redis、MinIO；基础设施文件同时把应用连接覆盖为容器 DNS。

两种模式都不得因停止或重建应用而修改基础设施数据。

- PostgreSQL 只创建 `POSTGRES_APP_DB`，Backend、Runtime Checkpoint 与 Memory 使用同一角色连接。
- Backend 以关闭 `baseline-on-migrate` 的 Flyway 初始化空库，Runtime 使用 `agent_run_checkpoint`，Memory 以幂等 DDL 管理 `agent_memory_*` 表。
- Redis 从空数据集启动，Backend 按需创建 MinIO Bucket。
- 所有初始化只补缺失资源，不导入、删除、覆盖或转换已有数据；
- 非空但无 Flyway 历史的 Schema 必须失败关闭。

## 配置准备

根目录 `.env.example` 是配置项的唯一模板，`.env` 必须与其保持相同键集合，只允许值不同。首次部署执行：

```bash
$ cp .env.example .env
$ ./scripts/sync-env.sh
$ unset COMPOSE_PROJECT_NAME
```

- 必须替换 PostgreSQL、Runtime Checkpoint、Redis、MinIO、LLM、内部令牌和 Boss 加密密钥。
- 启用 Memory 的 Embedding / Rerank 前，必须把模板中的 `sk-xxx` 替换为真实密钥；启用后查询与有界候选正文会发送给配置的模型服务。
- `AGENT_RUNTIME_DATABASE_URL` 使用 PostgreSQL URL 而非 JDBC，并指向 Flyway 管理的同一业务库；
- 内部令牌使用高熵随机值，Boss 密钥以 `openssl rand -base64 32` 生成。
- Flyway 创建的 `admin` 和 `user` 初始密码均为 `12345678`，应先在受控环境重置，再切换到 production。
- `.env` 不得提交、写入文档或日志，`.env.example` 只用于模板与渲染验证。

- 外部基础设施模式直接读取 `SPRING_DATASOURCE_URL`、`SPRING_REDIS_HOST`、`SPRING_REDIS_PORT`、`JOB_BUDDY_MINIO_ENDPOINT`、`JOB_BUDDY_MINIO_SECURE`、`AGENT_RUNTIME_DATABASE_URL`、`AGENT_MEMORY_DATABASE_URL` 和 `AGENT_MEMORY_DB_SSL_MODE`。
- 这些地址必须能从应用容器访问；
- 同机独立服务不能使用 `127.0.0.1` 或 `localhost` 指代宿主机，应使用容器可达的 DNS、专用网络地址或受控网关地址。
- 外部 PostgreSQL 必须同时允许 Backend JDBC、Runtime Checkpoint 和 Memory 使用对应角色访问同一业务库。

本地默认将应用和基础设施端口绑定到 `127.0.0.1`。服务器部署应在 `.env` 中显式设置浏览器访问地址和绑定策略，例如：

```dotenv
JOB_BUDDY_SERVER_HOST=job-buddy.example.com
JOB_BUDDY_BIND_HOST=127.0.0.1
JOB_BUDDY_INFRA_BIND_HOST=127.0.0.1
```

- 同机 HTTPS 反向代理下应用继续绑定回环地址；
- 只有确需外部直连时才绑定指定网卡或 `0.0.0.0`，并同时配置防火墙、TLS 与访问控制。
- 容器内的 `127.0.0.1` 表示容器自身，不能机械替换成服务器 IP。

## 启动与停止

### 仅应用模式

确认已独立部署的 PostgreSQL、Redis 和 MinIO 可从 Docker 容器访问后，只加载应用文件：

```bash
$ unset COMPOSE_PROJECT_NAME
$ docker compose --env-file .env -f docker-compose.yml up -d --build --wait
```

- 该模式由应用 Compose 创建 `${JOB_BUDDY_NETWORK_NAME}`，只负责八个应用容器之间的通信，不要求运行 `docker-compose-infra.yml`。
- 查看或停止时继续只使用应用文件：

```bash
$ docker compose --env-file .env -f docker-compose.yml ps
$ docker compose --env-file .env -f docker-compose.yml logs -f --tail=200
$ docker compose --env-file .env -f docker-compose.yml down
```

### 完整模式

需要同时部署 PostgreSQL、Redis 和 MinIO 时，按固定顺序叠加两个文件：

```bash
$ unset COMPOSE_PROJECT_NAME
$ docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose-infra.yml \
  up -d --build --wait
```

- 完整模式在同一个 Compose 项目中创建 11 个服务和共享网络。
- 基础设施文件将 Backend、Runtime 和 Memory 的连接覆盖为 `postgres`、`redis`、`minio` 等容器 DNS，并要求 Backend 等待三个中间件健康；
- Backend 完成 Flyway 后，Memory 创建自身表，Tool 依赖 Memory 与 Sandbox，Runtime 再依赖 Tool、Memory 与 Sandbox。
- 不得反转文件顺序，也不得用 baseline、repair 或手工历史表绕过校验。

查看、更新和停止完整环境时必须使用相同的文件组合：

```bash
$ docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose-infra.yml \
  ps

$ docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose-infra.yml \
  down
```

- 不得把 `down --volumes` 作为常规停止命令。
- 只有在完成 PostgreSQL 和 MinIO 可恢复备份、明确确认环境已经退役且数据可永久删除后，才允许对完整 Compose 项目执行卷删除：

```bash
$ docker compose --env-file .env \
  -f docker-compose.yml \
  -f docker-compose-infra.yml \
  down --volumes
```

该操作不可恢复，不属于应用发布、回滚或日常清理流程。

## 网络、端口与反向代理

- 两种模式都由 `APPLICATION_COMPOSE_PROJECT_NAME` 命名，并由应用文件创建 `${JOB_BUDDY_NETWORK_NAME}`。
- 仅应用模式通过环境文件中的可达地址访问数据库、缓存和对象存储；
- 完整模式增加 `postgres:5432`、`redis:6379`、`minio:9000` 三个容器 DNS。
- 禁止定义 Compose 保留变量 `COMPOSE_PROJECT_NAME`，否则会覆盖顶层 `name`；
- 部署前运行 `unset COMPOSE_PROJECT_NAME`。

Frontend 容器使用 Nginx 提供静态资源，并将相对路径 `/api` 代理到 `agent-backend:8080`，浏览器不需要知道 Backend 容器地址，也不需要为不同服务器重新构建前端。

- Nginx 请求体上限由 `NGINX_CLIENT_MAX_BODY_SIZE` 配置，默认 `1025m`，与 Spring 的默认 multipart 请求上限保持一致，避免合法上传在到达 Backend 前被代理层以 413 拒绝；
- 简历、智能引擎附件等具体端点仍由 Backend 执行业务级文件大小、类型与内容校验，代理层上限不能替代端点限制；
- Backend 对 Runtime、Intent、Memory、Tool、Eval 和 Sandbox 的调用与健康监控使用 `agent-runtime`、`agent-intent` 等 Compose 内部 DNS，不使用服务器公网 IP，也不发布这些服务端口。
- 内部地址由根环境文件的 `JOB_BUDDY_INTERNAL_RUNTIME_URL`、`JOB_BUDDY_INTERNAL_INTENT_URL`、`JOB_BUDDY_INTERNAL_MEMORY_URL`、`JOB_BUDDY_INTERNAL_TOOL_URL`、`JOB_BUDDY_INTERNAL_EVAL_URL` 和 `JOB_BUDDY_INTERNAL_SANDBOX_URL` 配置。
- 数据库中历史保存的 `127.0.0.1` 地址不会覆盖环境配置；
- 设置页只读展示实际生效地址。

- Backend 镜像为首次依赖连接、Flyway 校验和对象存储检查保留 300 秒健康检查启动宽限期。
- 宽限期内一旦健康端点成功即立即进入健康状态，不固定等待 300 秒；
- 启动失败仍按健康检查重试规则关闭部署。

- Nginx 为 SSE 关闭缓冲并设置长连接超时。
- 默认只发布 Frontend 与 Backend，Python 服务仅在共享网络可见；
- 基础设施端口绑定回环地址，生产不得直接暴露 PostgreSQL、Redis、MinIO API 或 Console。
- 生产建议只通过 HTTPS 反向代理公开 80/443，服务间使用内部令牌；
- Sandbox 只注入自身令牌和限制，不接收数据库、模型或对象存储密钥。
- Embedding / Rerank 密钥只允许在 Memory 容器中生效；应用 Compose 必须在 Runtime、Tool、Intent、Eval 和 Backend 容器中显式清空这两项共享环境变量。

## 镜像构建与受限网络

所有 Dockerfile 与 Compose 基础镜像均支持 `DOCKER_REGISTRY` 前缀，Python、uv、npm 和 Maven 下载源可独立配置。

默认使用官方源；受限网络可在 `.env` 中切换到组织可信 Registry 或代理：

```dotenv
DOCKER_REGISTRY=docker.m.daocloud.io
PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
NPM_CONFIG_REGISTRY=https://registry.npmmirror.com
MAVEN_REPO_URL=https://maven.aliyun.com/repository/public
```

- 镜像使用多阶段构建：Python 运行层只保留锁定环境与源码，Backend 使用 JRE，Frontend 只复制 Vite 产物，Tool 只安装 Boss 登录需要的 headless Chromium，Sandbox 保留 srt、Python、Node.js、JDK、bubblewrap、socat 和 ripgrep，并移除 npm 等构建工具。
- 镜像瘦身不能删除健康检查、内部鉴权、Boss 能力或沙箱隔离。
- 应用镜像使用 BuildKit cache mount 复用 Maven、pip、uv 和 npm 下载缓存；缓存只保存在构建器中，不会复制到最终运行镜像。Tool 的 Playwright 系统依赖和 Chromium 安装层位于业务源码层之前，普通 Python 源码变更不得触发浏览器重新安装。
- 日常发布不得使用 `--no-cache`、`docker builder prune`、`docker buildx prune` 或 `docker system prune`，否则会主动丢弃依赖缓存并显著增加后续构建时间；只有排查确定的缓存污染时才允许在受控范围内绕过或清理缓存。

### Sandbox 容器边界

Sandbox 的 Linux 容器必须启用轻量 init 作为 PID 1，以回收 `srt` 退出后被重新收养的 `socat`、`bwrap` 等孙进程，避免 zombie 持续占用受限 PID 配额；普通 restart 不会改变 init 配置，新增或修改该配置后必须强制重建容器。每次 srt 执行使用独立进程组，正常结束、异常和超时都必须按 SIGTERM 宽限、SIGKILL 兜底、wait 回收的顺序清理整棵进程树，避免用户命令或网桥进程越过请求生命周期。容器仍须以固定非 root 用户运行，丢弃全部 capability，启用 `no-new-privileges`、只读根文件系统、受限 `/tmp`、进程数、内存与 CPU 上限，并保持 `/workspace` 只读；不得使用 `privileged`、`CAP_SYS_ADMIN`、宿主目录或 Docker socket。普通 `/tmp` 必须保持 `noexec`；Python 一次性依赖单独使用容量受限、归属固定 Sandbox 用户的 `exec,nosuid,nodev` tmpfs，仅用于加载 wheel 原生扩展，依赖目录按请求销毁。`uv` 公共包下载缓存使用另一块容量受限的 `noexec` tmpfs，不得与普通 `/tmp` 或可导入依赖环境共用容量。srt 在容器内仍需创建 user、PID、mount 与 network namespace，Docker 默认 seccomp 会拦截这些调用，因此应用 Compose 仅对 Sandbox 容器设置 `seccomp=unconfined`，同时通过 `AGENT_SANDBOX_CONTAINER_ENABLE_WEAKER_NESTED_SANDBOX` 启用上游容器兼容模式。该兼容模式弱于原生 Linux 强模式，只能在前述外层补偿隔离完整存在时使用。

Docker 默认 `docker-default` profile 会阻止内层 bubblewrap 的 mount propagation。为保证同一套 Compose 在 macOS Docker 虚拟机与 Linux 宿主机运行，并避免宿主机安装自定义 AppArmor profile，应用 Compose 仅对 Sandbox 容器显式设置 `apparmor=unconfined`。该设置不关闭宿主机全局 AppArmor，也不影响其他容器；外层继续保留固定非 root 用户、全部 capability 丢弃、`no-new-privileges`、只读根文件系统、只读 workspace、受限临时目录与资源上限。不得添加 `CAP_SYS_ADMIN`、使用 privileged、挂载宿主目录或 Docker socket。

部署或更新后执行：

```bash
$ docker compose --env-file .env.server -f docker-compose.yml \
  up -d --build --force-recreate agent-sandbox
$ docker compose --env-file .env.server -f docker-compose.yml up -d --wait
```

`GET /health` 是进程存活检查，`GET /ready` 会以实际部署策略执行一次最小 srt 命令并短时缓存结果。Compose、Backend 服务监控和本地一键启动均以 `/ready` 作为 Sandbox 就绪条件，避免依赖存在但不能创建 namespace 时仍显示运行成功。

Backend 服务监控访问 Sandbox `/ready` 时使用独立的读取预算 `AGENT_SANDBOX_HEALTH_READ_TIMEOUT`，默认 20 秒并限制为最多 35 秒，与真实 srt readiness、进程清理和容器健康检查预算对齐。其他轻量 `/health` 探针继续使用短超时；不得用统一的 1.5 秒读取超时判断 Sandbox 不可用，否则单核服务器上的正常 namespace 初始化会被误记为服务故障。Sandbox `/ready` 的 2xx 响应还必须包含明确的正常业务状态，空正文、旧式纯文本或无法解析的正文不能按普通健康接口的兼容规则判定为就绪。

Sandbox 容器出现 `unhealthy` 时，使用只读诊断脚本采集容器健康历史、PID 上限与 zombie、真实 srt stdout/stderr、AppArmor/user namespace 和内核 OOM 线索。脚本默认读取 `.env.server` 与应用 Compose，不会重启、删除或修改容器：

```bash
$ ./scripts/diagnose-sandbox.sh
```

## 数据、升级与回滚

- 完整模式下，PostgreSQL、Redis、MinIO 和 Runtime workspace 都使用显式命名卷；
- 普通 `down` 不删除这些卷。
- Backend 在空库执行不可变基线和追加迁移，Runtime 与 Memory 使用同一数据库中的独立表。
- 升级前保留上一版镜像和配置，并备份 PostgreSQL 与 MinIO；
- 数据库结构必须向前兼容，故障修复通过更高版本补偿迁移完成。
- 只有当前 Schema 仍与上一版应用兼容时才能切回旧镜像，任何回退都不得重建基础设施卷或修改已发布迁移。

## 验证

提交部署修改前至少执行：

```bash
$ ./scripts/sync-env.sh
$ unset COMPOSE_PROJECT_NAME
$ sh -n scripts/sync-env.sh
$ bash -n scripts/diagnose-sandbox.sh
$ JOB_BUDDY_ENV_FILE=.env.example docker compose --env-file .env.example -f docker-compose.yml config --quiet
$ JOB_BUDDY_ENV_FILE=.env.example docker compose --env-file .env.example -f docker-compose.yml -f docker-compose-infra.yml config --quiet
$ ./.agent-harness/scripts/smoke_sandbox_container.sh
$ ./.agent-harness/scripts/gate.sh all --quick
```

- Docker 网络可用时还必须完整构建八个应用镜像，验证 Tool 的 Chromium headless 启动、Sandbox 真实 readiness、Python/Java/JavaScript 执行与文件/网络/Unix socket 隔离、Backend JRE 与所有服务健康检查，并分别验证仅应用模式的 8 个服务和完整模式的 11 个服务。
- 若镜像代理、Maven Central、外部模型或系统网络不可用，必须准确记录阻塞项，不得把配置渲染或部分测试通过描述为完整部署通过。
