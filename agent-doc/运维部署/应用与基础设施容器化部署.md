# Docker Compose 应用与基础设施部署

## 目标与边界

本方案用于在具备 Docker Compose 的 Linux 服务器部署 JobBuddy。`docker-compose-infra.yml` 管理 PostgreSQL、Redis 和 MinIO，`docker-compose.yml` 管理八个应用服务；两者通过 `JOB_BUDDY_NETWORK_NAME` 通信，但容器、卷和生命周期独立，停止或重建应用不会影响基础设施数据。

PostgreSQL 只创建 `POSTGRES_APP_DB`，Backend、Runtime Checkpoint 与 Memory 使用同一角色连接。Backend 以关闭 `baseline-on-migrate` 的 Flyway 初始化空库，Runtime 使用 `agent_run_checkpoint`，Memory 以幂等 DDL 管理 `agent_memory_*` 表。Redis 从空数据集启动，Backend 按需创建 MinIO Bucket。所有初始化只补缺失资源，不导入、删除、覆盖或转换已有数据；非空但无 Flyway 历史的 Schema 必须失败关闭。

## 配置准备

根目录 `.env.example` 是配置项的唯一模板，`.env` 必须与其保持相同键集合，只允许值不同。首次部署执行：

```bash
cp .env.example .env
./scripts/sync-env.sh
unset COMPOSE_PROJECT_NAME
```

必须替换 PostgreSQL、Runtime Checkpoint、Redis、MinIO、LLM、内部令牌和 Boss 加密密钥。`AGENT_RUNTIME_DATABASE_URL` 使用 PostgreSQL URL 而非 JDBC，并指向 Flyway 管理的同一业务库；内部令牌使用高熵随机值，Boss 密钥以 `openssl rand -base64 32` 生成。Flyway 创建的 `admin` 和 `user` 初始密码均为 `12345678`，应先在受控环境重置，再切换到 production。`.env` 不得提交、写入文档或日志，`.env.example` 只用于模板与渲染验证。

本地默认将应用和基础设施端口绑定到 `127.0.0.1`。服务器部署应在 `.env` 中显式设置浏览器访问地址和绑定策略，例如：

```dotenv
JOB_BUDDY_SERVER_HOST=job-buddy.example.com
JOB_BUDDY_BIND_HOST=127.0.0.1
JOB_BUDDY_INFRA_BIND_HOST=127.0.0.1
```

同机 HTTPS 反向代理下应用继续绑定回环地址；只有确需外部直连时才绑定指定网卡或 `0.0.0.0`，并同时配置防火墙、TLS 与访问控制。容器内的 `127.0.0.1` 表示容器自身，不能机械替换成服务器 IP。

## 启动与停止

先启动基础设施并等待健康检查通过：

```bash
docker compose --env-file .env -f docker-compose-infra.yml up -d --wait
```

基础设施项目创建三个独立命名卷和共享网络。首次空卷只生成统一应用库、Redis 空数据集和后续由 Backend 补齐的 MinIO Bucket；重复启动只做幂等检查。确认状态：

```bash
docker compose --env-file .env -f docker-compose-infra.yml ps
docker compose --env-file .env -f docker-compose-infra.yml logs --tail=200
```

随后构建并启动应用：

```bash
docker compose --env-file .env -f docker-compose.yml up -d --build --wait
```

Backend 是共享业务 Schema 所有者，先完成 Flyway 并健康；Memory 随后创建自身表，Tool 依赖 Memory 与 Sandbox，Runtime 再依赖 Tool、Memory 与 Sandbox。Backend 启动不等待这些 HTTP 下游，因为它们不参与基线初始化，但 Compose 最终等待全部健康。不得反转依赖，也不得用 baseline、repair 或手工历史表绕过校验。

查看应用状态与日志：

```bash
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs -f --tail=200
```

停止、更新或删除应用容器不影响基础设施：

```bash
docker compose --env-file .env -f docker-compose.yml down
```

需要停止完整环境时，必须先停止应用，再停止基础设施：

```bash
docker compose --env-file .env -f docker-compose.yml down
docker compose --env-file .env -f docker-compose-infra.yml down
```

不得把 `down --volumes` 作为常规停止命令。只有在完成 PostgreSQL 和 MinIO 可恢复备份、明确确认环境已经退役且数据可永久删除后，才允许对基础设施项目执行卷删除：

```bash
docker compose --env-file .env -f docker-compose-infra.yml down --volumes
```

该操作不可恢复，不属于应用发布、回滚或日常清理流程。

## 网络、端口与反向代理

两个项目分别由 `APPLICATION_COMPOSE_PROJECT_NAME` 与 `INFRASTRUCTURE_COMPOSE_PROJECT_NAME` 命名，共享 `${JOB_BUDDY_NETWORK_NAME}`。禁止定义 Compose 保留变量 `COMPOSE_PROJECT_NAME`，否则会覆盖顶层 `name` 并合并项目；部署前运行 `unset COMPOSE_PROJECT_NAME`。基础设施提供 `postgres:5432`、`redis:6379`、`minio:9000`，应用以 Compose DNS 通信。应用把共享网络声明为 external，因此基础设施必须先创建网络，但两者生命周期仍独立。

Frontend 容器使用 Nginx 提供静态资源，并将相对路径 `/api` 代理到 `agent-backend:8080`，浏览器不需要知道 Backend 容器地址，也不需要为不同服务器重新构建前端。

Nginx 为 SSE 关闭缓冲并设置长连接超时。默认只发布 Frontend 与 Backend，Python 服务仅在共享网络可见；基础设施端口绑定回环地址，生产不得直接暴露 PostgreSQL、Redis、MinIO API 或 Console。生产建议只通过 HTTPS 反向代理公开 80/443，服务间使用内部令牌；Sandbox 只注入自身令牌和限制，不接收数据库、模型或对象存储密钥。

## 镜像构建与受限网络

所有 Dockerfile 与 Compose 基础镜像均支持 `DOCKER_REGISTRY` 前缀，Python、uv、npm 和 Maven 下载源可独立配置。

默认使用官方源；受限网络可在 `.env` 中切换到组织可信 Registry 或代理：

```dotenv
DOCKER_REGISTRY=docker.m.daocloud.io
PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple
NPM_CONFIG_REGISTRY=https://registry.npmmirror.com
MAVEN_REPO_URL=https://maven.aliyun.com/repository/public
```

镜像使用多阶段构建：Python 运行层只保留锁定环境与源码，Backend 使用 JRE，Frontend 只复制 Vite 产物，Tool 只安装 Boss 登录需要的 headless Chromium，Sandbox 保留 srt、Node.js、bubblewrap、socat 和 ripgrep，并移除构建工具。镜像瘦身不能删除健康检查、内部鉴权、Boss 能力或沙箱隔离。

## 数据、升级与回滚

PostgreSQL、Redis、MinIO 卷由基础设施项目以显式卷名管理，Runtime workspace 卷属于应用项目。Backend 在空库执行不可变基线和追加迁移，Runtime 与 Memory 使用同一数据库中的独立表。升级前保留上一版镜像和配置，并备份 PostgreSQL 与 MinIO；数据库结构必须向前兼容，故障修复通过更高版本补偿迁移完成。只有当前 Schema 仍与上一版应用兼容时才能切回旧镜像，任何回退都不得重建基础设施卷或修改已发布迁移。

## 验证

提交部署修改前至少执行：

```bash
./scripts/sync-env.sh
unset COMPOSE_PROJECT_NAME
sh -n scripts/sync-env.sh
JOB_BUDDY_ENV_FILE=.env.example docker compose --env-file .env.example -f docker-compose.yml config --quiet
docker compose --env-file .env.example -f docker-compose-infra.yml config --quiet
./.agent-harness/scripts/gate.sh all --quick
```

Docker 网络可用时还必须完整构建八个应用镜像，验证 Tool 的 Chromium headless 启动、Sandbox 的 srt/Node/bwrap 命令、Backend JRE 与所有服务健康检查，并使用隔离项目名验证“停止应用不影响基础设施”。若镜像代理、Maven Central、外部模型或系统网络不可用，必须准确记录阻塞项，不得把配置渲染或部分测试通过描述为完整部署通过。
